# ARCANE 前端全量审查

阅读日期：2026-10-09。范围：`client/` 全部 80 个文件（10,361 行），以及 `components.json`、`vite.config.ts`、`vite.config.ts.bak`、`tsconfig.json`、`server/branding.test.ts`，合计 85 个文件、10,631 行。覆盖清单：`./阅读覆盖记录.json`。53 个默认 UI 组件共 6,189 行也已实际读取；遇到工具截断的区段已补读。未修改仓库文件。本报告基于源码与调用关系，没有启动浏览器；以下触发路径是可从代码确定的复现步骤，不能表述成已经完成浏览器端复现。

## 当前真实用户流程

- 路由仅 `/` 和 `/404`。首页直接挂载 `GameWorkspace`；Dashboard、Map、ComponentShowcase、AIChatBox 没有进入当前业务主流程。
- 新游戏：聊天输入或三条示例 → POST `/api/game/stream` → SSE 状态／解释文本 → 澄清卡片（可能出现）→ 一次性接收完整 artifact → 展示 iframe、文件与源码 QA。
- 修改：有 artifact 后，聊天发送改为非流式 `/api/trpc/game.patch?batch=1` 请求；不是新游戏流式管线。
- 手工编辑：Monaco 编辑本地 `files` 数组；点击 Save version 时调用版本存储，但预览与 JSON 始终使用另一个 `artifact` 状态。
- 登录／项目：Manus OAuth；可创建项目和切换项目 ID，切换不载入项目内容。
- 下载：浏览器 JSZip 打包本地 files，并额外写入 `game.artifact.json`。
- 历史：后端 query、加载／恢复／下载函数已声明，当前 JSX 没有版本列表和操作入口。因此“首页可以预览／回滚历史版本”的旧概述不成立。
- 运行 QA：iframe 是 `sandbox="allow-scripts"`，无 allow-same-origin，能隔离直接读写宿主 DOM；QA 报告通过 postMessage 返回。

## 必须优先修复的确定性问题

### F01：编辑、预览、JSON、导出不是同一份文档（P1）

证据：`client/src/components/GameWorkspace.tsx:79` 与 `:80` 保存重复状态；`:122` 从 artifact 创建预览；`:224` 手工编辑只 setFiles；`:228` 保存新 artifact 的临时对象，不 setArtifact；`:231` ZIP 分别使用 files 和旧 artifact。

触发：生成一个游戏，修改 index.html，再点击 Restart／Reload／Save version／Download ZIP。结果：编辑器和 ZIP 中的 index.html 是新代码，但预览、Game JSON 及 ZIP 的 game.artifact.json 仍是旧代码。源码 QA、build 状态也仍引用编辑前结果。用户无法验证修改，恢复 artifact 的消费者可能得到不同版本。

建议：单一 canonical workspace document；draftFiles 与 savedRevision 必须明确区分，预览与下载全部使用同一 snapshot。维护 contentHash／dirty flag，人工编辑即令静态／运行 QA 失效；显式 Run 应对当前 draft 编译、运行并报告结果。保存后更新 revision 并清除 dirty，而不是把两份状态各自继续维护。

### F02：切换项目不切换内容，跨项目保存错误（P1）

证据：`:256` 的 ProjectPicker `onSelect={setActiveProjectId}`；`:131` 的 persist 仅按当前 activeProjectId 写入；`:117` 新建项目也只更改 ID。没有依据项目 ID 载入 artifact、files、会话或最新版本的 effect。

触发：项目 A 内生成游戏，选择项目 B，继续编辑或发送修改。B 的标题／ID 已切换，A 的内容仍显示，后续保存可能进入 B。新建项目也继承当前旧画布。完整页面刷新又把 activeProjectId 重置为空，所有作品内容无法自动恢复。

建议：`/projects/:projectId` 路由 + 获取 latestVersion + per-project 工作区；切换前处理未保存 draft，变更项目必须取消或隔离当前任务，数据缓存以项目／版本为 key。新游戏应明确新建文档／新项目，避免只重置画面。

### F03：历史管理代码没有界面入口（P1 产品断点）

证据：`:99` versionsQuery；`:232` loadHistoricalVersion；`:245` downloadSavedVersion；`:125` ensureProject。全文 JSX 中均没有调用历史加载／下载，也没有读取 versionsQuery.data；ensureProject 从未调用。CSS 中 version-strip 等样式是遗留。

触发：登录并保存版本，用户只能看到成功 toast，无法从界面查看／预览／回滚／下载该历史版本。登录后未主动从项目下拉创建／选择项目，Save version 也只弹出信息而不进入创建项目流程。

建议：作品页／项目抽屉、可分页版本时间线，缩略图、变更摘要、版本 diff、预览与恢复入口。首个保存应直接创建项目再保存；匿名创作应保留本地草稿，登录后认领，不要导航后丢失作品。

### F04：Patch 的 Stop 按钮无作用，任务生命周期存在竞态（P1）

证据：`:211`—`:221` 的 handlePatch 没有 AbortController 和 signal；`:271` Stop 仅 `abortRef.current?.abort()`；`:256` New Game 生成中可点且没有 abort；`:104`—`:115` 没有 runId；无组件卸载时 abort 的 cleanup。

触发：发起修改，点击 Stop，请求仍继续。新游戏生成未完成时点 New Game，旧请求完成后重新 setArtifact 覆盖新画布。任务中选择其他项目或者编辑代码也不会隔离旧结果。手工修改可被晚到的生成／修改结果覆盖。

建议：统一 generation／patch／clarify 任务状态机；每次任务携带 immutable projectId、baseRevision、jobId、runId；客户端 AbortController 与服务端取消都接通；仅接受当前文档、当前任务、当前基线的结果。取消应展示明确状态；关闭／切换应保存草稿并停止或转后台。

### F05：QA postMessage 不验来源也不验结构，可使宿主界面崩溃（P1）

证据：`GameWorkspace.tsx:104`—`:108` 仅调用 isProbeMessage，然后 setProbe；共享 `runtimeProbe.ts:63`—`:70` 仅检查 source 字符串和 report 的 typeof object；`:274` 直接执行 probe?.checks.some，`:282` 执行 probe.checks.map，`:283` 读 probe.errors。

触发：任意能向当前页面 postMessage 的 window，或生成游戏自身执行 `parent.postMessage({source:'arcane-runtime-probe',report:{}},'*')`。类型检查会通过，渲染对 undefined checks 调用 some／map 后进入全局 ErrorBoundary。合法外观的伪造报告也能把 QA 显示成全部通过。旧 iframe 的晚到报告可能覆盖新预览。

建议：iframe ref 校验 `event.source === iframe.contentWindow`；opaque origin 下不能用 origin 单独判断可信，增加 nonce／runId；Zod 验证完整 report、列表长度、枚举与文本上限；拒绝过期 report。独立自动化 QA 结果应来源于受控测试进程，不能当作生成代码能控制的可信证书。

### F06：保存并未真正 await，潜在恢复流程会谎报成功（P1，当前恢复函数无 UI 入口）

证据：`:131` async persist 内部使用 `saveVersion.mutate`，不返回／等待保存 Promise；`:220` await persist 立即结束；`:239`—`:241` await persist 后无条件 toast 恢复成功。

触发：存储调用失败或延迟。Patch spinner 在保存仍 pending 时结束；未来接上历史入口后，版本恢复会在保存未完成时显示“已恢复并保存为新版本”，最终保存可能失败。saveVersion.onSuccess 也会在用户继续编辑时把状态覆盖成旧操作的 Saved。

建议：持久化使用 mutateAsync，明确 draftReady／saving／saved／saveFailed，服务器确认后才标记保存成功；请求固定 revision，晚到 save 回调不能覆盖当前文档状态。恢复只在新版本提交成功后更新项目 head。

### F07：澄清状态串到下一次创作，第二轮澄清协议不完整（P2）

证据：`:154` 总是发送 answersRef.current；`:177` 长期合并 answers；`:146` 新请求不清空 answers；`:206` 取消也不清空；只有 New Game 清空。`:184`—`:203` 的第二份 stream parser 不处理 clarify，不特殊处理 AbortError，submitClarifyAnswers 也无 isGenerating 防重入。

触发：上一游戏回答了玩法／主题，再从示例或取消后的请求创作另一款游戏，旧答案进入新 prompt。服务端第二轮仍需要澄清时，界面不展示问题；按 Stop 显示 error toast 而非取消；快速重复提交有机会并发启动多个请求。

建议：答案绑定 conversation／generationId；澄清轮次由后端结构化状态驱动，取消和新请求建立新会话；所有轮次用同一 parser／状态机，防双击，取消处理一致。前端继续输入也应支持修改意图和选择默认项。

### F08：SSE 重复实现，断流与尾部事件缺乏处理（P2）

证据：`:156`—`:167` 与 `:188`—`:198` 手写 parser 两份；仅按 `\n\n` 拆帧、单行 data 正则、JSON.parse；done 时未 flush decoder／buffer，也未检查是否收到了 complete／clarify。

触发：服务器／代理提前结束响应，或最后一帧未以双换行结束。UI finally 解锁但没有最终成功／错误结论，可能停在正在生成状态、保留空助手消息。CRLF 或标准 SSE 的多行 data 不被可靠支持。

建议：使用标准 SSE parser／单一 useGameGeneration hook；事件 schema、eventId、序号、终态必须完整；无终态断流是明确失败并给重试／恢复操作。生成解释 token 可节流合并更新，避免每个 token 都遍历所有 messages。

### F09：多文件树／ZIP 已有，预览只支持单文件 index.html（P1 能力边界）

证据：`client/src/lib/gamePreview.ts:17` 仅寻找 index.html，`:21` 仅取其内容，`:34` 直接注入探针返回；无文件路径重写、虚拟文件系统、打包或构建产物。

触发：index.html 引用 `./game.js`、`./style.css` 或本地 assets。srcDoc 相对 URL 解析到宿主服务，不会读取 artifact.files，因而引用失败；TypeScript／package.json 工程也不会自动编译。文件树不能代表真实可运行多文件项目。

建议：短期明确单文件 HTML 契约并限制生成；中期受控构建器支持指定版本的 Phaser／Three.js 等引擎，形成 asset manifest 和构建产物，再由专用预览域服务；不要任意 npm install 宿主机。产物 URL／资源加载逻辑与 ZIP 采用同一构建配置。编辑语言也扩展 JavaScript／CSS，目前 language 函数与 enum 只支持 TS、JSON、Markdown、HTML、text。

### F10：人工编辑和历史加载沿用旧质量结果／成功标签（P2）

证据：`:141` 总写 Build passed；`:224` 编辑不清空 build／validation／probe；`:237` 载入任意历史版本时人工构造 status passed；`:238` 未清空旧 trace／validation／intent；`:256` New Game 也未清空这些状态。

触发：把 index.html 改成语法错误，QA 面板仍能绿点；新画布保留前一款游戏的静态结果与构建日志；未来历史 UI 接通后，老版本同样显示新版本检查结论。

建议：每份检查绑定 contentHash／revision／engineVersion 和 executedAt；内容变更即 stale，不把“保存成功／结构检查通过／实际构建通过／运行通过／玩法验收通过”混成一个 Passed 标签。产品主界面用用户可理解的状态，细节留在展开面板。

## 其他确定性问题和能力缺口

- **开发日志可能保存会话凭据（P1，仅开发态）**：`client/public/__manus__/debug-collector.js:473` 原样拷贝 Headers，`:485` 写进 entry，没有 sanitizeValue；reportLogs 原样 JSON.stringify。`client/src/main.tsx:57` 的 Bearer 会进入开发日志。`vite.config.ts:84` 的 transformIndexHtml 在 production 条件下不注入该脚本，不能说生产默认泄露。修复是在采集时即脱敏 Headers、URL query、敏感 body，生产完全禁用；调试请求大小和写盘也要有限额。Vite 日志端点 `:135`—`:136` 无请求体大小限制，`:63` 同步 appendFileSync 可能阻塞开发服务器。
- **认证／错误流程不统一（P2）**：`main.tsx:45` 支持 sessionStorage Bearer 和全局认证错误处理；GameWorkspace 的三个裸 fetch（`:154`、`:186`、`:215`）绕开该处理。若这些接口需要认证，Cookie 被阻断时与 tRPC 主客户端行为不一致；当前是否保护接口应由后端审查确认。生成可用匿名时不能声称这些 fetch 一定登录失败。
- **保存前没有首建／草稿恢复（P1 产品）**：ensureProject 死代码。默认 activeProjectId null，生成后的 persist 静默返回。浏览器刷新、登录导航丢掉所有前端作品和会话；不应把这称为可靠自动保存。
- **工作台没有自动滚动、会话持久化、版本 diff、修改确认和 undo（P2）**：messages 仅 useState，工作台没有滚动 ref／effect；已有 AIChatBox 的 scrollToBottom 也只在发送时触发，而且该组件未被主流程使用。模型长解释时用户看不到最新内容，失败后没有从未完成步骤重试的入口。
- **没有作品公开／分享／探索／游玩指标／remix（产品能力缺口）**：App 路由只有首页和 404。客户端不存在发布链接、私有访问控制页面、Explore、创作者页、排行榜／多人服务或作品卡片。此项是对已确认 Google Playground 公开功能的差距，不意味着短期应一次完成所有社交功能。
- **没有素材／场景／参数编辑（产品能力缺口）**：不存在图片上传、参考图、sprite／动画／音效资源管理、对象选中修改、玩法参数面板。除聊天改整段文件之外，没有低成本可控编辑路径。
- **默认 UI 体系与主页面样式脱节（P2 维护／可访问性）**：53 个组件大部分是 Radix／shadcn 薄封装，但 `index.css` 仅声明字体 token，没有组件依赖的 primary、popover、border 等主题颜色 token；大量主样式直接硬编码色值并使用 important。`ui/sonner.tsx:1` 读取 next-themes，App 使用自己 contexts/ThemeContext，二者 provider 不相连；toast 样式还引用未定义 CSS 变量。统一一套 token 与 ThemeContext 后再谈主题扩展。
- **浏览器存储异常能阻断首页（P2）**：`useAuth.ts:54` 在 useMemo 渲染期直接写 localStorage，无 try/catch。禁用存储或 SecurityError 时抛异常进入全局边界。移到 effect，失败退回内存；token 的 sessionStorage 读取已有 try/catch，可按同样防御。
- **404／异常体验与产品不一致（P2）**：NotFound 是亮色通用模板；ErrorBoundary 对所有用户展示完整 error stack，仅提供刷新；用户有未保存 draft 时刷新会丢数据。改为错误编号、可恢复草稿和诊断展开。
- **无效按钮／移动端限制（P2）**：`GameWorkspace.tsx:258` More options 无 handler；Console 的 Run again 只 setTab(run) 显示下载说明，不运行；Run 页无执行 action。`index.css:16` 在小于 900px 隐藏 project-picker 和 user-chip，手机没有项目切换入口。`client/index.html:8` viewport maximum-scale=1 禁用用户缩放，正文／状态普遍 9–12px，需改善可访问性。
- **可维护性和前端验证不足（P2）**：核心主组件 287 行但包含大量单行极长 JSX，约 20 组状态和重复 parser。拆成文档／任务状态、聊天、预览桥、项目历史、编辑器、QA；默认组件暂不需要大量业务化改造。branding.test.ts 只测试环境变量而非渲染的品牌；缺少覆盖真正高风险流程的前端 integration／E2E。tsconfig 排除 tests，测试类型问题可能不被 tsc 覆盖。
- **遗留／未使用组件不应被误报成产品功能**：Map、Dashboard、ComponentShowcase、AIChatBox、ManusDialog 是模板基础设施／组件演示，并未在当前路由业务中使用。Map 的脚本加载失败 Promise 不 reject、重复挂载加载脚本是确定性维护缺陷，但优先级低于业务主流程。

## 面向顶级平台的前端优化顺序

### 阶段 A：先把可靠创作工作区做实

目标：生成、修改、编辑、预览、保存、导出始终指向同一个版本；用户刷新和取消任务不会丢作品。

1. Single workspace store／reducer，明确项目 ID、draft、head revision、dirty、job state、validation contentHash。
2. 接通项目切换与历史抽屉，首建即持久化，匿名本地 draft 在登录后可认领。
3. 统一新建／澄清／patch 的流式客户端和取消流程，防竞态、断流恢复。
4. 预览当前 draft，消息桥绑定 iframe／runId 并验证 schema；QA 状态按 revision 失效。
5. 用 Playwright 验证高价值旅程：生成→编辑→预览一致→保存→刷新恢复；A/B 切换不串内容；取消不应用晚到结果；非法 probe 不崩溃；失败保存不显示成功。

### 阶段 B：把创作入口变成游戏产品而非代码工具

1. 第一屏提供优质作品示例、类型卡片、参考图与清晰预期；生成时展示真实进度和可重试状态。
2. 默认以试玩为中心，源码／JSON／管线细节放进开发者模式；新手主要看操作说明、玩法规则与可编辑参数。
3. 增加可控修改：选中对象→修改外观／大小／速度／碰撞参数；模型修改前后展示影响摘要和 diff，允许撤回。
4. 多文件与素材支持以可靠构建产物为前提；上传／生成资产具有来源、规格、版本、加载错误反馈。
5. 移动端支持完整项目操作、触控输入与安全区域，不仅把 iframe 缩成 330px。

### 阶段 C：加入分享与作品循环

优先最短闭环：可直接玩的发布 URL + 私有／公开状态 + 作品封面 + remix。随后做 Explore、作者页、点赞／收藏／游玩时长／版本更新，最后按玩法需求加入排行榜和多人。Google Playground 刚发布的官方产品特征是可参考的目标，不应把未验证的产品宣传当成我们代码已经具备的能力，也不宜先堆社交页再修核心保存可靠性。

## 建议验收指标

这些是建议目标，不是现有测量值：

- 文档一致性：编辑器／预览／导出／恢复对同一 revision 的内容哈希一致率 100%。
- 数据可靠性：刷新恢复、项目切换、版本恢复的集成测试全通过；失败保存不能误报成功。
- 任务可靠性：所有任务都支持取消；结束事件完整率与过期结果拒绝率可观测。
- 编辑体验：生成→首次可玩耗时 p50/p95、修改→可玩耗时、编辑后玩法回归率。
- 产品效果：首次创作完成率、从首玩到第一次修改的转化、发布率、作品被他人玩／remix 的比例。

以上指标应该使用真实埋点与固定样本测量，不能凭工作台 Passed 字样估计。
